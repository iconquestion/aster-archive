# 架构

**状态：当前架构说明。** 本文件解释系统由什么组成、如何连接及为何这样装配。产品意图以[产品与关卡意图](./product-game-intent.md)为准；接口和运行时行为以[系统契约](./system-contract.md)为准；验证方式以[验证](./verification.md)为准。

## 当前边界

系统当前包含首页、起始页、更新页和已实现的 `01`–`26` 关，以及支撑它们的 HTTP、HTTPS、HTTP/2、WebSocket、会话持久化和运行能力。关卡持续、不定期更新，不采用阶段边界。新增关卡或运行能力应同步补充本文件中受影响的模块、数据流和部署边界。

## 组成

```text
浏览器 / 协议客户端
        │
        ├─ 常规 HTTP ── Web 入口层 ── Express 应用
        │                                  ├─ public/ 静态页面与资源
        │                                  ├─ src/levels/ HTTP 路由
        │                                  └─ 配置、日志、健康检查
        │
        └─ 特殊协议直连 ── Node 协议服务
                                   ├─ WebSocket（15）
                                   ├─ HTTPS Trailer（17）
                                   └─ HTTP/2 + Early Hints（21）

Express 状态型关卡（25、26） ── Cookie 会话 ── JSON 状态文件
```

### 静态内容

`public/` 承载页面、脚本、样式、字体和其他静态线索。静态内容由 Express 统一托管；页面或资源本身可以是谜题的一部分，因此不要把常规重构假定为无风险。

### HTTP 关卡

`src/levels/` 以关卡划分后端路由。`src/app.js` 负责挂载路由和中间件。按关卡拆分优先于通用“谜题引擎”：每关的请求语义、线索载体和失败路径差异很大，而维护者应能直接定位具体关卡。

### 协议型关卡

WebSocket upgrade、HTTPS Trailer 和 HTTP/2 stream 需要 Node 较低层的 server 能力；`src/createServers.js` 将它们与 Express 装配。它们不强行塞进同一代理路径，因为部署层可能无法透明转发相应协议。部署时应允许客户端连接系统契约定义的协议入口。

### 状态与持久化

第 25、26 关使用 Cookie 将玩家映射到独立 JSON 状态文件。文件持久化是有意的低成本选择：状态量小、可检查、易于本地调试；代价是必须显式处理会话隔离、文件缺失、损坏与过期。状态字段和错误语义由系统契约定义。

### 运行支撑

- `src/config.js`：加载并校验配置。
- `src/logger.js`：运行日志与按日轮转。
- `src/index.js`：进程入口和优雅停机。
- `src/createServers.js`：HTTP/HTTPS/HTTP2/协议服务装配。
- `GET /api/status`：健康检查。

## 关键运行流

1. 常规页面或 HTTP 请求由 Web 入口层转入 Express；静态资源直接从 `public/` 返回，API 由对应关卡路由处理。
2. 协议型请求连接对应 Node 服务，协议反馈本身就是游戏线索的一部分。
3. 第 25、26 关收到请求后读取当前 Cookie 对应状态；写操作验证输入和规则、重算状态并原子地写回。不同会话不得读取或修改彼此状态。

## 维护约束与取舍

- 采用 Node/Express 单体：当前规模下页面、API、协议与测试在一个仓库中更易同步；不以多节点或独立数据库为目标。
- 特殊协议保留独立入口：优先保证玩家能真实接触协议能力，而非追求统一代理外观。
- 测试按风险和玩法分层：HTTP 与状态逻辑适合自动化；HTTP/2 Early Hints 等依赖真实客户端行为的场景保留人工验收，详见[验证](./verification.md)。

当协议入口、会话/持久化模型、运行配置或服务装配变化时，更新本文件；接口字段、状态码和验收规则分别更新系统契约与验证，而不要在此复制。
