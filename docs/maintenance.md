# 维护指南

首次配置和启动见 [README](../README.md#本地运行)。关卡要表达的玩法见[产品与关卡意图](./product-game-intent.md)，接口、状态码和会话规则见[系统契约](./system-contract.md)。

## 服务组成

[进程入口](../src/index.js)加载配置、初始化日志、启动三个监听服务，并处理停机。[Express 应用](../src/app.js)提供 `public/` 下的页面和资源、`src/levels/` 中按关卡划分的 API，以及健康检查 `GET /api/status`。

| 监听服务 | 本地示例端口           | 用途                                        |
| -------- | ---------------------- | ------------------------------------------- |
| HTTP     | `8080`（`HTTP_PORT`）  | 页面、普通 API、第 15 关 WebSocket 升级     |
| HTTPS    | `8443`（`HTTPS_PORT`） | 同一 Express 应用，第 17 关使用响应 Trailer |
| HTTP/2   | `9443`（`HTTP2_PORT`） | 第 21 关的 Early Hints 及其脚本             |

配置从 `config/.env` 加载，`APP_ORIGIN` 用于跨源响应。HTTPS 和 HTTP/2 共用配置中的 TLS 私钥和证书。日志写入仓库下的 `logs/`，按日轮转。 [配置加载](../src/config.js) · [配置示例](../config/.env.example) · [监听服务](../src/createServers.js)

第 25、26 关按 Cookie 将玩家会话映射到独立的 JSON 文件，更新时直接写入对应文件。第 25 关处理请求时会顺带清理超过 12 小时未修改的会话文件。 [第 25 关](../src/levels/25.js) · [第 26 关](../src/levels/26.js)

## 部署与协议验收

部署变更后，用玩家实际访问的入口复测下表。反向代理需要转发 WebSocket 升级并保留相关响应信息。代理无法转发对应协议时，需要提供可直连的服务入口。

| 关卡                    | 怎么验                                                                                                                                                                                                            | 当前实现与覆盖                                                                                                                  |
| ----------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------- |
| 15 · WebSocket          | 连接 `/api/15/challenge`，确认收到欢迎消息。发送 `{"action":"init"}` 后检查地图尺寸，再从页面验证迷宫操作。                                                                                                       | 自动化检查 HTTP 端的握手和欢迎消息。页面在 HTTPS 下会连同源 `wss:`，Node 的升级处理挂在 HTTP 监听器上，经反代访问时须确认转发。 |
| 17 · HTTPS Trailer      | 用支持 Trailer 的 HTTPS 客户端请求 `/api/17`，检查响应头中的 `Trailer` 声明，再读取响应结束后的 Trailer，确认能找到第 18 关线索。                                                                                 | 自动化在本地 HTTPS 端验证 Trailer。页面当前使用线上协议地址。                                                                   |
| 21 · HTTP/2 Early Hints | 用能显示临时响应的 HTTP/2 客户端请求 `/api/21`。确认 `103` 比 `200` 先到，且 `103` 中的 `Link` 将 `analytics.js` 标为待预加载的脚本。再访问同一 HTTP/2 入口下的 `/api/analytics.js`，确认脚本能提供第 22 关线索。 | 本地 Node 客户端已观察到 `103` 和 `200`。页面当前使用线上协议地址，部署入口仍需按上述步骤检查。                                 |

人工验收时记录日期、执行人、客户端版本、访问入口和结果。异常时保留必要的网络记录或截图。

## 自动化测试

按 README 配好 `config/.env` 和 TLS 文件后，在仓库根目录运行 `npm test`。只验证协议时，可以运行 `npm test -- --runTestsByPath test/protocol/protocol.test.js`。

Windows 下，若从非系统盘运行时因 `/tmp` 会话目录权限导致测试启动失败，可切到系统盘，用绝对路径指定 Jest 入口和 `--config`。

| 测试                 | 覆盖                                                                                                                                                                                                                               |
| -------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 基础运行             | 健康检查、配置加载、日志轮转和停机处理。 [健康检查](../test/http/status.test.js) · [日志](../test/logger.test.js) · [停机](../test/index.test.js)                                                                                  |
| 普通 HTTP 与静态线索 | 第 01–14 关通过正式 Express 应用检查旗标、静态资源和接口，其中第 08 关逐层验证目录索引。后续关卡的 HTTP 用例使用独立的测试应用。 [关卡测试](../test/http/levels.test.js)                                                           |
| 特殊协议             | 第 15 关的握手和欢迎消息、第 17 关的 Trailer。测试在本机随机端口监听。 [协议测试](../test/protocol/protocol.test.js)                                                                                                               |
| 会话关卡             | 第 25 关的会话隔离、提交和恢复，以及第 26 关的棋盘初始化、会话复用、库存、失败分支和取旗规则。两关都使用临时状态目录。第 26 关的成功取旗测试使用预置的已解棋盘，完整操作流程留给手工验证。 [关卡测试](../test/http/levels.test.js) |

第 11、19、21、23 关在自动化中显式跳过。第 21 关按上表验证，其余三关按下节复查。

## 浏览器与主线复核

- **第 11、19、23 关**分别手工走一遍多步解码、字体与源文本比对、页面脚本与本地存储的解谜流程。 [关卡题解（含剧透）](./reference/level-solutions.md)
- **第 25、26 关**从页面复查第 25 关的离线保护和恢复，以及第 26 关从新棋盘到通关的完整流程。
- **改动页面或线索资源时**，从上一关取得入口，验证能打开本关，并按题面推进到下一关。第 13 关的 sitemap 使用正式站点的绝对 URL。本地验收时，将 `<loc>` 中的路径接在本地地址后，确认展品和草稿都能打开。 [站点地图](../public/13-k9c3x6n2tw/sitemap.xml)
- **改动题面或提示时**，确认页面有可识别的关卡标题，提示说清特殊访问前提并引导观察，首页、起始页和关卡页的命名与进度说明一致。
