## 05

### 设计目标

让玩家观察 HTTP 请求方法，并尝试用不同的方法访问同一个接口。

### 文案与知识点的结合

「推一下门」失败后，Hint 问是不是「打开方式」有问题。同一扇门对应同一个 URL，换一种打开方式对应换一个 HTTP 请求方法。

### 实现方式

页面通过 `get_json_response('push', 'responseMsg', '/api/05')` 发起默认的 `GET`。`src/levels/05.js` 分别处理 `GET` 和 `POST`。

### 解题步骤

1. 点击「推一下门」。在网络面板中找到返回 `405` 的 `GET /api/05`，它的 `Allow` 响应头列出了 `POST`。
2. 向同一路径发送 `POST /api/05`，请求体可以留空。也可以在关卡页的控制台运行下面的请求。

   ```js
   await fetch('/api/05', { method: 'POST' }).then((response) =>
     response.json()
   );
   ```

3. 请求返回 `200`。从 `message` 中门背后的字条读出下一关入口。

### 答案

`06-m4v7q2c9ta`

## 10

### 设计目标

让玩家阅读 JavaScript 校验函数，为十张照片补全浪漫数字。

### 文案与知识点的结合

「亲手拾起」对应给每张照片补上一个浪漫数字。「拼出那份旧日的浪漫」落实为按这些数字重新排列照片。

### 实现方式

每张照片的初始浪漫值是 DOM ID 的十进制字符编码，旁边标出对应的 ASCII 字符。填写浪漫数字后，页面实时显示合计和合计除以 `11` 的余数。首张照片作为基准，其余照片的余数相同时显示绿色对号，不同时显示红色错号。输入非法或重复的浪漫数字时，涉及的输入框会标红。

三项条件全部勾选后才能点击「浪漫排序」。十张照片都要填入 `0–9` 中的一个数字，每个数字恰好用一次，十个余数还要通过 `IsRomantic` 校验。按钮按浪漫数字从小到大排列照片。

页面底部的「当前计算Flag」按照片的当前顺序拼接初始浪漫值对应的字符。还没有填入有效数字的位置用 `?` 占位。照片已完成排序且三项校验都通过时，flag 旁显示绿色对号，其余状态显示红色错号。

### 解题步骤

1. 查看源码中的 `modulus` 和 `IsRomantic`。每张照片的合计对 `11` 取余，十个结果必须相同。
2. 枚举公共余数 `0–10`。从公共余数中减去照片的初始浪漫值，再按模 `11` 换算成 `0–10`，就得到该照片需要填的数字。排除包含 `10` 或重复数字的方案后，只剩公共余数 `1`。
3. 按页面上的照片顺序填入下表的数字。正确时，每张照片右侧的余数都是 `1`。

   | 照片日期     | 初始浪漫值 | 浪漫数字 | 合计  | Flag 字符 |
   | ------------ | ---------- | -------- | ----- | --------- |
   | `2006/09/14` | `119`      | `3`      | `122` | `w`       |
   | `1998/11/03` | `51`       | `5`      | `56`  | `3`       |
   | `2003/07/12` | `114`      | `8`      | `122` | `r`       |
   | `2010/01/22` | `102`      | `9`      | `111` | `f`       |
   | `2001/04/09` | `99`       | `1`      | `100` | `c`       |
   | `2008/02/21` | `54`       | `2`      | `56`  | `6`       |
   | `1995/06/18` | `118`      | `4`      | `122` | `v`       |
   | `2004/12/02` | `50`       | `6`      | `56`  | `2`       |
   | `2007/05/30` | `115`      | `7`      | `122` | `s`       |
   | `1999/08/27` | `111`      | `0`      | `111` | `o`       |

4. 点击「浪漫排序」。照片按浪漫数字 `0–9` 排列后，底部会把初始浪漫值对应的字符拼成 `11-oc6wv32srf`，并标为正确。用这个 flag 打开下一关。

### 答案

`11-oc6wv32srf`

## 12

### 设计目标

让玩家学习发现隐藏入口、爆破简单口令，并在拿到会话后继续访问受保护接口。

### 实现方式

- 开机后，在欢迎页点击「搭载最新 AI 系统!」五次，再点「开始」。主菜单会显示「管理员入口」。

- 登录成功会下发一个名为 `bibilabu` 的 Cookie。

- 管理员面板查询 13 号房间时会显示配送备注，其中有绕过封闭楼梯的路线和下一关旗标。

### 解题步骤

1. 查看页面里的隐藏逻辑。

   点击"搭载最新 AI 系统!" 5 次后，`adminEntryUnlocked = true`，才会显示"管理员入口"。

2. 显示入口后，找到登录接口。

   `POST https://www.iconquestion.com/api/12/login`

   表单参数：

   ```txt
   username=admin
   password={四位数字密码}
   ```

   这一关的关键是不要被"管理员登录"吓住，因为题目真正想让玩家尝试的是四位数爆破。

3. 查看当前实现中的密码生成机制。

   当前实现会在服务端代码中，基于固定 secret 和当天日期生成一个当日有效的四位数字密码。

   这个密码：
   - 每天轮换一次
   - 同一天内保持稳定
   - 保留前导 `0`，因此应视为四位数字字符串而不是普通数字
   - 在服务进程内按天缓存，因此高频爆破时不会为每次请求重复计算哈希

   因此这一关的设计思路就是对管理员密码进行四位数爆破。

4. 观察爆破出正确密码后的返回结果。

   ```json
   { "message": "登录成功" }
   ```

   同时设置 Cookie，例如：

   ```http
   Set-Cookie: bibilabu=<当日四位密码>; Path=/api/12/get_room_info; HttpOnly; ...
   ```

5. 继续请求受保护接口。

   `GET https://www.iconquestion.com/api/12/get_room_info?room_id=13`

   并携带刚才的 Cookie。

6. 查看响应的 `message`。配送备注提示走屋外应急楼梯，「联系电话」后是下一关旗标。

   ```json
   {
     "message": "配送备注：请将货品放在门口，不要按门铃。通往三楼的楼梯已封闭，请走屋外应急楼梯。收件人：flag，联系电话：13-k9c3x6n2tw"
   }
   ```

### 答案

`13-k9c3x6n2tw`

## 15

### 设计目标

让玩家学习 WebSocket 相关知识，并根据服务端的交互反馈一步步推进状态。

### 实现方式

页面不是普通的一次性 HTTP 提交，而是要求玩家建立 WebSocket 连接，并在交互过程中根据反馈不断调整动作。

为了降低难度，页面中已经设计好了 WebSocket 相关代码，玩家只需要进行操作即可。

### 解题步骤

如只希望通关，则玩家只需按照常规逻辑进行游玩，不需要任何前后端知识。

唯一的难点在于，网页并未提供 GUI 游戏显示界面，玩家需要使用其他方法记忆当前状态。

为了控制难度，迷宫生成大小固定 5x5，玩家可以轻易通关。

如果希望深入探究 WebSocket 知识，或者假定网页未给出任何现成的 WebSocket 代码，则玩家需要按照下面的步骤进行分析解题。

1. 先查看页面前端写死的地址，并尝试建立 WS 连接。

   ```js
   const wsUrl = `${wsProtocol}//${location.host}/api/15/challenge`;
   ```

2. 建立连接后，先观察服务端返回的提示消息。

   ```json
   { "message": "WebSocket connected. Please send { action: 'init' }" }
   ```

3. 按提示先发送初始化消息。

   ```json
   { "action": "init" }
   ```

4. 服务器返回地图尺寸。

   ```json
   { "x": 5, "y": 5 }
   ```

5. 之后开始发送移动指令。

   ```json
   {"action":"move","direction":"up"}
   {"action":"move","direction":"right"}
   ```

6. 每次发送移动指令后，观察普通响应中的状态反馈。
   - 撞墙：`{"wall":1,"win":false}`
   - 走通：`{"wall":0,"win":false}`

7. 到达终点后，查看服务端返回内容。

   ```json
   {"wall":0,"win":true,"flag":"16-7kq2m9x4bz","maze":[...]}
   ```

这一关的关键是理解服务端会根据移动结果持续反馈状态。拿到地图尺寸后，可以手工试探，也可以按撞墙反馈逐步搜索可行路径，直到到达终点。

### 答案

`16-7kq2m9x4bz`

## 16

### 设计目标

让玩家学习根据接口分支条件修改请求参数和请求头，而不是只按页面默认方式访问接口。

### 实现方式
